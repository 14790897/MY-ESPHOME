# ESP-NOW 低功耗设备的可靠唤醒

## 背景

ESP-NOW 门锁系统：

- **被控端**（电池）：ESP32-C3，deep sleep 周期唤醒，醒来监听 30ms
- **网关**（有线）：ESPHome + ESP-NOW，转发 HA 指令

被控端两种周期：白天 1s 睡 + 30ms 醒，夜间 20s 睡 + 30ms 醒。
网关每天 7:00 发"切白天"、22:00 发"切夜间"。

## 问题

早上经常切不过去。约 60~70% 概率收不到命令，门锁一整天停在夜间模式。

## 第一版（错误）

被控端 20s 醒一次，那发送窗口盖过 20s 就行了：

```yaml
# 每 6s 发一次, 11 次 = 66s 窗口
repeat:
  count: 11
  then:
    - espnow.send: { data: [0x04] }
    - delay: 6s
```

66s >> 20s，理论上至少能命中 3 个唤醒窗口。为什么不灵？

因为漏了一半：**覆盖时长够了，但发送间隔没落进唤醒窗口里**。

```
被控端醒来(30ms):  |--|                |--|                |--|
                  t=0               t=20s              t=40s

网关发送(6s间隔):  ↑   ↑   ↑   ↑   ↑   ↑   ↑   ↑   ↑   ↑   ↑
                   0   6  12  18  24  30  36  42  48  54  60s
```

被控端 t=20s 醒的那 30ms，网关要等到 t=24s 才发；t=40s 醒的，要等到 t=42s。
单次命中率只有 **30ms / 6000ms = 0.5%**。

## 两个条件

```
覆盖时长 > 睡眠周期        ← 至少经历一次完整的"睡→醒"
发送间隔 ≲ 唤醒窗口        ← 窗口里必然含有一次发送
```

按标称值配好：

```yaml
# 25ms 间隔 < 30ms 窗口, 840×25ms = 21s > 20s
repeat:
  count: 840
  then:
    - espnow.send: { data: [0x04] }
    - delay: 25ms
```

看着很完美。**但拿设备实测后发现，这四个数字全是错的。**

## 实测（2026-10-11）

| 标称 | 实测 |
|---|---|
| 白天周期 1s | **1.64s** —— 每次醒来要先花 ~0.64s 做 WiFi/ESP-NOW init |
| 发送间隔 25ms | **48–51ms**（白天）/ **89ms**（夜间全失败） |
| 唤醒窗口 30ms | **~0.64s 射频在线** |
| `espnow.send` 发完就走 | **要等 MAC 层 send report 才返回** |

第二条：ESPHome 的 `espnow.send` **`wait_for_sent` 默认是 true**
（`espnow/__init__.py:198`），而且组件一次只发一包（`espnow_component.cpp:332`）。
每包 = `delay 25ms` + 对端 ACK 了 ~23ms / 没 ACK（MAC 重试耗尽）~64ms。

第三条：门锁醒来做 WiFi init 的那 ~0.64s 里射频在线、MAC 层照常回 ACK ——
哪怕 ESP-NOW 的接收回调还没注册、应用层根本收不到这一包。

两条叠加，30ms 的应用层窗口才总能被撞上。

## 结论

```
保证命中 ⟺ 覆盖时长 > 睡眠周期 且 单次发送的空中占用（含重试）≳ 唤醒窗口
```

几个坑：

- **"发送间隔"不是你写的 `delay`**，是 `delay + 等 MAC send report 的时间`。
- ⚠️ **`ESP_NOW_SEND_SUCCESS` / send report 只代表对端射频 ACK 了，不代表应用层收到。**
  白天 45 包测出 34–36 个"成功"，实际投递寥寥。唯一可信的判据是应用层应答。
- 标称值基本都是假的（这套系统里 1s 实测 1.64s、30ms 实测对应 ~0.64s），先实测再算。
- 所以公式只用来定方向，**最终判据永远是实测按键成功率**。
